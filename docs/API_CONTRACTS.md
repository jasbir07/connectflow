# ConnectFlow — API Contracts

## 1. API Conventions

- Base path: `/api/v1`
- Request and response format: JSON
- Dates and timestamps: ISO 8601 in UTC
- Identifiers: opaque strings generated by the service
- Content type: `application/json`
- Error responses use a consistent structure.
- Protected application and consent routes will require authentication when authentication is implemented.

## 2. Common Error Format

Example:

{
  "error": {
    "code": "CONSENT_REQUIRED",
    "message": "Valid consent is required for this operation.",
    "requestId": "req-example-001"
  }
}

Do not return stack traces, credentials, or internal implementation details to callers.

## 3. Create an Application

### Request

POST `/api/v1/applications`

{
  "programmeCode": "SKILL-01"
}

### Successful Response — 201 Created

{
  "applicationId": "app-example-001",
  "programmeCode": "SKILL-01",
  "status": "DRAFT",
  "createdAt": "2026-10-14T10:00:00Z"
}

### Possible Errors

- `400` — Invalid request
- `401` — Authentication required, once authentication is enabled
- `500` — Unexpected server error

The server generates the application ID and status; clients cannot choose them.

## 4. Get Application Details

### Request

GET `/api/v1/applications/{applicationId}`

### Successful Response — 200 OK

{
  "applicationId": "app-example-001",
  "programmeCode": "SKILL-01",
  "status": "AWAITING_CONSENT",
  "createdAt": "2026-10-14T10:00:00Z",
  "updatedAt": "2026-10-14T10:05:00Z"
}

### Possible Errors

- `401` — Authentication required
- `403` — Caller lacks permission to view the application
- `404` — Application not found

## 5. Record a Consent Decision

### Request

POST `/api/v1/applications/{applicationId}/consents`

{
  "purpose": "Verify eligibility for SKILL-01",
  "requestedFields": [
    "subjectRef",
    "programmeCode",
    "eligibilityStatus"
  ],
  "decision": "GRANTED",
  "expiresAt": "2026-10-21T10:00:00Z"
}

### Successful Response — 201 Created

{
  "consentId": "consent-example-001",
  "applicationId": "app-example-001",
  "purpose": "Verify eligibility for SKILL-01",
  "requestedFields": [
    "subjectRef",
    "programmeCode",
    "eligibilityStatus"
  ],
  "decision": "GRANTED",
  "grantedAt": "2026-10-14T10:10:00Z",
  "expiresAt": "2026-10-21T10:00:00Z",
  "revokedAt": null
}

### Possible Errors

- `400` — Invalid decision or fields
- `401` — Authentication required
- `403` — Caller cannot manage consent for this application
- `404` — Application not found

Only the authenticated applicant or an appropriately authorised actor may make a consent decision. Production consent requirements need separate legal and security review.

## 6. Revoke Consent

### Request

POST `/api/v1/applications/{applicationId}/consents/{consentId}/revocation`

{
  "reason": "User withdrew permission"
}

### Successful Response — 200 OK

{
  "consentId": "consent-example-001",
  "decision": "REVOKED",
  "revokedAt": "2026-10-14T10:15:00Z"
}

Revocation prevents new protected-data retrievals under that consent. The prototype will document how in-flight exchanges are handled; revocation cannot undo information already lawfully retrieved or cancel an external operation automatically.

## 7. Request an Eligibility Check

### Request

POST `/api/v1/applications/{applicationId}/eligibility-checks`

Header:
`Idempotency-Key: check-app-example-001`

Body:

{
  "consentId": "consent-example-001"
}

The backend must verify access to the application, verify the consent scope and validity, and ensure the required requested fields are covered before calling the registry.

### Successful Response — 202 Accepted

{
  "exchangeId": "exchange-example-001",
  "applicationId": "app-example-001",
  "status": "PROCESSING"
}

This operation may be synchronous in the first implementation while still returning a consistent exchange resource. If processing becomes asynchronous, the client can poll the exchange status.

### Possible Errors

- `400` — Invalid request
- `401` — Authentication required
- `403` — No permission to access the application
- `404` — Application or consent not found
- `409` — Request conflicts with current state
- `422` — Consent is denied, revoked, expired, or has insufficient scope
- `502` — Invalid response from the registry
- `503` — Registry unavailable

A retry with the same idempotency key must return the existing operation result rather than create a duplicate operation.

## 8. Get an Exchange

### Request

GET `/api/v1/exchanges/{exchangeId}`

### Successful Response — 200 OK

{
  "exchangeId": "exchange-example-001",
  "applicationId": "app-example-001",
  "status": "SUCCEEDED",
  "result": {
    "programmeCode": "SKILL-01",
    "eligibilityStatus": "ELIGIBLE"
  },
  "createdAt": "2026-10-14T10:20:00Z",
  "completedAt": "2026-10-14T10:20:01Z"
}

The result contains only the fields approved for this operation and caller. The example is synthetic.

### Possible Errors

- `401` — Authentication required
- `403` — Caller is not authorised to view this exchange
- `404` — Exchange not found

## 9. Get an Application Timeline

### Request

GET `/api/v1/applications/{applicationId}/timeline`

### Successful Response — 200 OK

{
  "applicationId": "app-example-001",
  "events": [
    {
      "type": "APPLICATION_CREATED",
      "occurredAt": "2026-10-14T10:00:00Z"
    },
    {
      "type": "CONSENT_GRANTED",
      "occurredAt": "2026-10-14T10:10:00Z"
    },
    {
      "type": "ELIGIBILITY_CHECK_COMPLETED",
      "occurredAt": "2026-10-14T10:20:01Z"
    }

}

Only authorised users can view the timeline. Event details must not expose unnecessary personal data.

## 10. Internal Eligibility Registry Contract

This mock service is called by ConnectFlow, not directly by the browser.

### Request

POST `/internal/v1/eligibility-checks`

{
  "subjectRef": "USER-101",
  "programmeCode": "SKILL-01",
  "requestedFields": [
    "subjectRef",
    "programmeCode",
    "eligibilityStatus"
  ]
}

### Successful Response — 200 OK

{
  "subjectRef": "USER-101",
  "programmeCode": "SKILL-01",
  "eligibilityStatus": "ELIGIBLE",
  "sourceRecordRef": "ELIG-9001"
}

The mock service must validate requested fields, return only allowed fields, and use synthetic records. Its service-to-service authentication will be defined before implementation.

## 11. Idempotency and Failure Semantics

- Store the idempotency key with the operation and its final outcome.
- Scope keys to the authenticated caller and operation.
- Reuse of a key with a different request body returns `409 Conflict`.
- Retry transient failures with bounded attempts and backoff.
- Do not retry every error; invalid input and denied consent require a different response.
- Record an exchange state transition for each meaningful outcome.
- Never report an exchange as successful until the required result and state changes have been durably recorded.

## 12. Open Contract Decisions

- Final authentication approach
- Exact source-registry authentication mechanism
- Whether the eligibility request will be synchronous or asynchronous
- Retention period for audit metadata
- Pagination conventions for timeline and audit endpoints

These are intentionally open until the relevant implementation requirements are reviewed.
